# Turn Forge

`turn-forge` — учебный C++ backend-проект для пошаговой игровой логики и сетевого сервиса.

## Где ведём задачи

Все задачи ведём в **GitHub Projects**.

Правило простое: если работы нет в таске, значит её не существует.

Для каждой задачи должны быть:

```text
название
описание
исполнитель
статус
ссылка на pull request(ы), когда он(и) появится
```

Если в процессе работы стало понятно, что задача слишком большая, её нужно разбить на несколько маленьких.

## Статусы задач

В проекте используются такие статусы:

```text
Todo
Opened
In Progress
Review
Need changes
In trunk
Done
```

### `Todo`

Идеи или не расписанные задачи.

В этом статусе задача ещё не готова к разработке. У неё может не быть полного описания, критериев готовности или понятного результата.

Задачу нельзя брать в работу из `Todo`, пока она не расписана.

### `Opened`

Задача расписана и готова к тому, чтобы её взяли в работу.

У задачи в `Opened` должны быть:

```text
понятное описание
ожидаемый результат
критерии готовности
```

Разработчик берёт задачу из `Opened` и переводит её в `In Progress`.

### `In Progress`

Задача взята в работу.

В этом статусе разработчик пишет код в отдельной разработческой ветке.

Для задачи должен быть создан branch от `trunk`, например:

```text
heesooyaam/12-game-session
heesooyaam/21-invalid-move-validation
```

### `Review`

Код написан, открыт pull request.

В этом статусе задача ожидает ревью.

Pull request должен быть направлен в `trunk`.

### `Need changes`

Ревьюер нашёл замечания после ревью.

Разработчик исправляет замечания в той же ветке и снова отправляет задачу на `Review`.

### `In trunk`

Ревью пройдено, pull request смержен в `trunk`.

Это значит, что задача уже попала в основную разработческую ветку, но ещё не обязательно попала в релиз.

### `Done`

Задача завершена и попала в релизную ветку.

`Done` означает, что задача не просто смержена в `trunk`, а уже находится в релизе.

## Ветки

В проекте используется trunk-based workflow.

Основная идея: актуальная разработка быстро попадает в `trunk`, а релизные ветки периодически отводятся от `trunk`.

## `trunk`

`trunk` — основная ветка разработки.

В ней всегда должен лежать рабочий код.

Все изменения после проверки попадают в `trunk`.

Напрямую писать код в `trunk` нельзя. Изменения попадают туда через pull request из короткоживущей разработческой ветки.

## `release/*`

Релизные ветки отводятся от `trunk`.

Примеры:

```text
release/0.1
release/0.2
release/mvp
```

В релизные ветки нельзя добавлять новые большие фичи.

В `release/*` допускаются только:

```text
исправления багов
мелкие правки
подготовка к сдаче или релизу
```

Если баг исправлен в `release/*`, этот фикс обязательно должен попасть обратно в `trunk`.

## Разработческие ветки

Код пишем только в короткоживущих разработческих ветках.

Разработческая ветка создаётся от `trunk`.

Формат имени:

```text
<GITHUB_USER_NAME>/<task-id>-short-name
<GITHUB_USER_NAME>/<task-id>-short-name
<GITHUB_USER_NAME>/<task-id>-short-name
<GITHUB_USER_NAME>/<task-id>-short-name
```

Примеры:

```text
heesooyaam/12-game-session
heesooyaam/18-websocket-handshake
heesooyaam/21-invalid-move-validation
heesooyaam/25-game-rules-tests
```

После завершения работы открывается pull request:

```text
feature/... -> trunk
```

После ревью и проверки ветка мержится в `trunk`.

## Рабочий процесс

Перед началом работы обновить `trunk`:

```bash
git checkout trunk
git pull
```

Создать ветку под задачу:

```bash
git checkout -b feature/12-game-session
```

Перевести задачу в GitHub Projects в статус:

```text
In Progress
```

Работать только в своей разработческой ветке.

Проверить изменения:

```bash
git status
git diff
```

Закоммитить:

```bash
git add . # или путь до файла/папки, которую хочешь добавить
git commit -m "Add game session"
```

Запушить ветку:

```bash
git push -u origin heesooyaam/12-game-session
```

Если поменял что-то еще, снова добавляешь, делаешь коммит и пушишь, но писать "-u origin heesooyaam/12-game-session" не надо

Открыть pull request:

```text
heesooyaam/12-game-session -> trunk
```

И покликать в ui, должно быть что-то вроде "Create pull request"

Перевести задачу в статус:

```text
Review
```

Если после ревью есть замечания, ревьюер переводит статус в:

```text
Need changes
```

Когда разработчик начал исправлять замечания, задача переводится в статус:

```text
In Progress
```

Когда pull request смержен в `trunk`, задача переводится в:

```text
In trunk
```

Когда изменения попали в релизную ветку, задача переводится в:

```text
Done
```

## Pull request

В pull request нужно указать:

```text
какую задачу решает PR
что было сделано
как проверить
какие есть ограничения или спорные места
```

PR не должен быть слишком большим. Лучше несколько маленьких PR, чем один огромный.

В PR не должно быть случайных файлов:

```text
build/
cmake-build-*/
.vscode-server/
.idea/
*.log
```

## Коммиты

Коммит должен описывать, что было сделано.

Нормальные примеры:

```text
Add game session model
Implement move validation
Fix draw detection
Add game rules tests
Refactor websocket connection handler
```

Плохие примеры:

```text
fix
update
changes
работает
asdf
```

## Стиль C++

В проекте используем C++20.

Базовые правила:

```text
фигурные скобки на той же строке
у if/for/while всегда есть фигурные скобки
имена переменных и функций — snake_case
имена классов — PascalCase
одна ответственность на класс/функцию
не смешивать форматирование и логику в одном PR
```

Пример:

```cpp
if (is_valid_move) {
    apply_move(move);
}

for (int i = 0; i < players_count; ++i) {
    update_player_state(i);
}
```

## Работа на dev-тачке

Разработка ведётся на удалённой dev-тачке.

Гайд по подключению лежит здесь:

```text
docs/dev-machine-guide.md
```

Обычно рабочая папка проекта на dev-тачке:

```text
~/projects/turn-forge
```

## Что нельзя делать

Нельзя:

```text
коммитить напрямую в trunk
писать фичи в release/*
пушить приватные ключи
пушить токены, пароли и .env с секретами
пушить build-директории
мержить свой PR без проверки
брать задачу в работу, не переведя её в In Progress
переводить задачу в Done, если она ещё не попала в релиз
```

## Что делать, если что-то непонятно

Если задача непонятна, не надо молча писать код наугад.

Нужно:

```text
написать вопрос в задаче или в чат
уточнить ожидаемое поведение
при необходимости обновить описание задачи
только потом писать код
```

## Definition of Done

Задача считается готовой, когда:

```text
код написан в отдельной разработческой ветке
открыт pull request
проект собирается
тесты проходят, если они есть (пока не настроен ci, скинуть пруф, что тесты прошли)
код прошёл ревью
PR смержен в main
изменения попали в release/*
карточка задачи переведена в Done
```
