================================================================================
СПЕЦИФИКАЦИЯ И ПРАВИЛА ВАЛИДАЦИИ БИБЛИОТЕКИ NHttp (HTTP/1.1)
================================================================================

Настоящий документ описывает модель данных, правила валидации, контракты работы 
с заголовками и краевые случаи (подводные камни) перед сериализацией запросов 
(THttpRequest) и ответов (THttpResponse) по стандарту RFC 9110 / RFC 9112.

--------------------------------------------------------------------------------
1. ПОДДЕРЖИВАЕМЫЕ ПРОТОКОЛЫ, МЕТОДЫ И СТАТУС-КОДЫ
--------------------------------------------------------------------------------

* Версия протокола:
  - Поддерживается строго HTTP/1.1 (THttpVersion(1, 1)).
  - Любые другие версии отклоняются валидатором.

* Поддерживаемые HTTP-методы (EHttpRequestMethod):
  - GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS.
  - Значение NOT_SET запрещено к отправке.

* Поддерживаемые статус-коды ответов (EHttpResponseStatus):
  - 101 SWITCHING_PROTOCOLS
  - 200 OK
  - 201 CREATED
  - 204 NO_CONTENT
  - 400 BAD_REQUEST
  - 401 UNAUTHORIZED
  - 403 FORBIDDEN
  - 404 NOT_FOUND
  - 500 INTERNAL_SERVER_ERROR
  - 501 NOT_IMPLEMENTED
  - Значение NOT_SET запрещено к отправке.

--------------------------------------------------------------------------------
2. ПРАВИЛА ДЛЯ Transfer-Encoding И Content-Length (FRAMING RULES)
--------------------------------------------------------------------------------

1. Взаимоисключение:
   - Заголовки Content-Length и Transfer-Encoding НЕ МОГУТ присутствовать 
     одновременно ни в запросах, ни в ответах (защита от Smuggling / Desync).

2. Content-Length:
   - Встречается не более одного раза.
   - Содержит только десятичные цифры 0-9 (без знаков +, -, пробелов).
   - Значение заголовка обязано байт-в-байт совпадать с размером тела (body.size()).

3. Transfer-Encoding:
   - Поддерживает как раздельные заголовки, так и списки через запятую 
     (например, "Transfer-Encoding: gzip, chunked"). Парсер автоматически 
     разбивает значения по запятым и обрезает пробелы (OWS trim).
   - Пустые элементы между запятыми (например, "gzip, , chunked") запрещены.
   - Токен "chunked" (регистронезависимо) обязан встречаться СТРОГО 1 РАЗ во всей 
     цепочке кодирований. Повторный "chunked" запрещён стандартом.
   - Токен "chunked" обязан быть СТРОГО ПОСЛЕДНИМ элементом цепочки кодирований.

4. Обязательность фрейминга (Явное указание):
   - Если сообщение содержит непустое тело (!body.empty()), пользователь ОБЯЗАН 
     явно добавить в THttpHeaders либо Content-Length, либо Transfer-Encoding: chunked.
   - Автоматического вычисления и добавления длины при сериализации не производится 
     (явное предпочтительнее неявного). Если фрейминг отсутствует при наличии 
     тела — валидатор отклонит сообщение.

--------------------------------------------------------------------------------
3. СПЕЦИФИКА ВАЛИДАЦИИ ЗАПРОСОВ (THttpRequest)
--------------------------------------------------------------------------------

* Target (URI):
  - Обязан начинаться со слеша '/'.
  - Содержит только печатные символы URI (согласно таблице HTTP_CHAR_TARGET_LUT).
  - Все знаки процента '%' (percent-encoding) обязаны сопровождаться ровно двумя 
    валидными hex-символами (%XX).

* Заголовок Host:
  - Обязан присутствовать в запросе строго в 1 экземпляре.
  - Значение не должно быть пустым.

* Методы без тела (GET, HEAD):
  - Заголовок Transfer-Encoding категорически запрещён.
  - Заголовок Content-Length либо отсутствует вовсе, либо равен строго "0".

--------------------------------------------------------------------------------
4. СПЕЦИФИКА ВАЛИДАЦИИ ОТВЕТОВ (THttpResponse)
--------------------------------------------------------------------------------

* Запрет Host:
  - Заголовок Host является strictly Request-only полем. В ответах он СТРОГО 
    ЗАПРЕЩЁН и приводит к ошибке валидации.

* Заголовок Date:
  - Обязан присутствовать ровно в 1 экземпляре для всех финальных ответов 
    (статусы 200–501).
  - Обязан строго соответствовать стандарту IMF-fixdate / RFC 9110 
    (ровно 29 байт, таймзона GMT, например: "Sun, 09 Aug 2026 21:29:33 GMT").
  - Для статуса 101 SWITCHING_PROTOCOLS заголовок Date не требуется.

* Ограничения по статус-кодам:
  - 101 SWITCHING_PROTOCOLS: Запрещены Content-Length и Transfer-Encoding.
  - 204 NO_CONTENT: Запрещен Transfer-Encoding. Content-Length либо 
    отсутствует, либо строго равен "0".
  - 201 CREATED: Обязателен заголовок Location (строго 1 штука, непустой). 
    Допускаются как относительные пути (/users/42), так и абсолютные URL 
    (https://example.com/users/42).
  - 401 UNAUTHORIZED: Обязателен заголовок WWW-Authenticate (непустой, 
    со схемой аутентификации, например: Bearer realm="api").

--------------------------------------------------------------------------------
5. ЛИМИТЫ И СИНТАКСИС ЗАГОЛОВКОВ
--------------------------------------------------------------------------------

* Лимит количества полей:
  - Общее количество полей заголовков не должно превышать MAX_COUNTER_HEADERS.

* Имена заголовков (Name):
  - Не пустые, состоят только из допустимых символов токена tchar 
    (HTTP_CHAR_NAME_LUT). Пробелы перед двоеточием запрещены.

* Значения заголовков (Value):
  - Содержат только печатные символы ASCII (HTTP_CHAR_VALUE_LUT).

* Безопасность (Инъекции):
  - Ни в именах, ни в значениях заголовков не допускаются символы перевода 
    строк '\r', '\n' (CRLF Injection) и null-байт '\0'.
